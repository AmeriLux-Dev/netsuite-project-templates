# {{appTitle}}

Suitelet-hosted React application for NetSuite, scaffolded by create-netsuite-project (`react-app` template). `HOW-TO-USE.md` has the longer explanation of commands and layout; `README.md` records the purpose, owners, dependencies, deployment, support and decisions of this application and is written by the people who own it.

## Commands

| Command | Use it for |
|---|---|
| `npm run generate` | Regenerate `api/src/repositories/generated/` and `api/src/types/models.gen.ts` from the models, then `api/src/scripts.gen.ts` and `client/src/api/` from the controllers and the jobs. Run after touching a model, a controller or a job. |
| `npm run typecheck` | `tsc --noEmit` in every workspace. |
| `npm run lint` | ESLint over the repository, then `scripts/checkStructure.mjs`: every script's pieces agree (a controller's or job's declaration, its exports, its SDF object). |
| `npm test` | Vitest in `api/` and `client/`. |
| `npm run build` | Client (Vite) then API (webpack) into `netsuite/FileCabinet/SuiteScripts/{{appName}}/`. |
| `npm run dev` | Vite on port 3000 plus the local restlet proxy on port 4000. Needs `client/.env`. |
| `npm run deploy` / `npm run deploy:files` | Deploy to the account in `project.json`. Only when the person asked for it. |
| `npm run add:jobs` | Add what Map/Reduce jobs need, once per project: the run record, the daily cleanup script, the `jobRuns` endpoint and the `useJobRun` hook. Adds nothing that is already there. |

Every root command runs `npm run generate` first, once; a workspace script run directly (`-w api`) assumes it has run.

Before a commit: `npm run typecheck`, `npm run lint`, `npm test`.

## Adding a script

There are four kinds: a controller (an API the client calls), a job (background work), a user event and a client event. Follow the step-by-step recipe in `HOW-TO-USE.md`, "Adding a controller", "Adding a job" or "Adding an event". A controller is the controller file, its SDF object, `npm run generate`, then a hook. A job adds `npm run add:jobs` first (once per project) and a service that owns the run's input and result shapes; an event is one self-contained file whose script record you create in NetSuite by hand. The VS Code snippets in `.vscode/netsuite-project.code-snippets` (controllers `nspControllerRestlet` / `nspControllerSuitelet` with `nspControllerShapes`, `nspControllerEndpoint`, `nspControllerParse`, `nspControllerAuthorize`; jobs `nspJob` with `nspJobReduce` and `nspJobParameter`; events `nspUserEvent` and `nspClientEvent`; `nspService`; repositories `nspRepository` with `nspRepositoryCreate` / `nspRepositoryUpdate`, `nspRepositorySuitelet`, `nspRepositoryModule`; `nspSpecification`; `nspModel`, `nspHelpModel`, `nspModelSubrecordClass`, `nspModelBase` with one `nspModel<Decorator>` fragment per decorator (a sublist line is `nspModel` plus `nspModelInternalId` and `nspModelParentId`); `nspRepositoryLog`; `nspNetsuiteIds`; tests `nspTestController`, `nspTestService`, `nspTestRepository`, `nspTestRepositorySuitelet`, `nspTestHook`; client `nspHookQuery`, `nspHookQueryWith`, `nspHookMutation`, `nspPage`, `nspRoute`; and `nspObjectRestlet` / `nspObjectSuitelet` / `nspObjectMapReduce` in XML) emit each file in the shape the rules below expect; the table in `HOW-TO-USE.md`, ".vscode/", maps prefix to file. The `user` controller is the live reference. A script's ids are written once, in its controller's or job's declaration (an event's in the event file); a record's ids once, on its model. `npm run lint` fails until all the pieces are present and agree.

## Where things live

- The two halves share one file, `netsuite.ts` at the root. `api/` is SuiteScript, `client/` is React, and the client's whole view of the backend is generated (`client/src/api/`) from the controllers.
- `netsuite.ts` at the root holds `app` (the application's names and File Cabinet files) and any id no controller or model owns (script parameters, saved searches, list values). Exported constants and types only, no imports: both the SuiteScript bundle and the browser bundle include it directly.
- The wire (the response envelope, the endpoint types, `ScriptDeclaration`, `ScriptRef`) comes from `@amerilux/netsuite-api`; `api/` imports its `/server` entry, `client/` its `/client` entry.
- The `user` controller (one endpoint, `roles`: the caller and every role assigned to them) with its `UserRolesPage` is the starting point, and the `userRoles` Suitelet it calls is the pattern for a script that must run as another role (its deployment has `<runasrole>ADMINISTRATOR`, its declaration `browser: false`). Build on them or replace them; `HOW-TO-USE.md` walks through every multi-file addition step by step.
- `api/src/jobs/<name>.ts`: one Map/Reduce job per file, layered like a controller. `defineJob` declares the stages and the script in one call: `getInputData` takes the run's input and answers the work, `map` does one item, `reduce` gathers a key, `summarize` returns the run's result. A stage calls a service; `N/*` and repositories are out of bounds, as in a controller. The input and result shapes belong to the service, so whatever starts a run and whatever does the work speak the same types. Export the stages the job has and `summarize` always: the run is closed there, and a job that answers nothing declares no `summarize` (or returns `void`) while still exporting it, leaving the run's result `null`. A job answers nothing, so every run is a row in `customrecord_{{prefix}}_job_run`: a service starts one with `startJobRun(jobs.<name>, input)` (the repository `npm run add:jobs` wrote) and gets the run id, an endpoint gives it to the page, and `useJobRun({ job, runId })` polls it until it ends (409 when every deployment of the job is already running). Progress comes from the task, so it is null once the run ends: `stagePercentComplete` is the stage being worked, not the run, and starts again at each stage, while `itemsProcessed` and `itemsTotal` are that stage's row counts and only go up — show the counts. A refresh loses the run id but not the run: called with no run id, the hook asks the `jobRuns` controller's `mine` endpoint for the caller's own runs of that job and picks up the one still going, and a run that is gone comes back as `isMissing` rather than an error. Run records are removed daily by the cleanup job. The folder and the machinery around it exist once `npm run add:jobs` has been run.
- `api/src/events/user/<subject>.ts` and `api/src/events/client/<subject>.ts`: self-contained SuiteScript that belongs to a NetSuite record, not to this application. A user event works the record its context carries, logs with `N/log`, and reaches anything else through a repository function; a client event runs in the browser, calls `N/*` itself, logs with `console`, and is built without telemetry. The ids an event uses are written at the top of the event file. Events have no SDF object: their script records and deployments are created in NetSuite by hand.
- `api/src/` is flat per layer and the file name carries the layer: `userController.ts`, `userService.ts`, `activeUserRepository.ts`, `employeeRolesSpecifications.ts`, `models/EmployeeRole.ts`. Services, repositories and specifications are named after what they handle (a subject, a data source, a record type), not after a controller. The underscore folder `_host/` is boilerplate; nothing is added to it.
- `api/src/controllers/<name>Controller.ts`: the whole controller in one file. The `@NScriptType` header, then the request and response shapes (DTOs: an entity type from `api/src/types/models.gen.ts`, a type a service returns, a `Pick` of one, or a composition of several; the wire, not the record), then `<name>Endpoints = defineEndpoints({ ... })`: one transport-agnostic function per endpoint (`list`, `byId`, `create`), its parameter the request and its return value the response, then `export type <Name>Endpoints = typeof <name>Endpoints`, then the entry point with the script declaration: `export const post = defineRestlet({ name: '<name>', scriptId, deployId }, <name>Endpoints)` for a Restlet or `export const onRequest = defineSuitelet({ ..., browser: false }, ...)` for a Suitelet. The declaration creates nothing; the ids can be changed to match the record and deployment in NetSuite and the generated client follows. Every call is a POST whose JSON body carries the request and an `endpoint` property naming the endpoint; there is no HTTP method to choose. `defineEndpoints`, `defineRestlet`, `defineSuitelet` and `ApiError` come from `@amerilux/netsuite-api/server` and supply the envelope, error mapping and timing. A file becomes a deployed script only when its leading JSDoc carries `@NScriptType`; everything else under `api/src/` is bundled into the scripts that import it. An endpoint is the only code that knows the wire: it unpacks the request, calls a service with plain arguments, and shapes the response from what the service returns, written out field by field so a field added to a service's type later does not reach the wire unasked; a wire-level check such as coercing an id sent as a string lives here, not in the service. Switching transport touches the header, the entry point and the SDF object, nothing else. The define call takes options after the endpoints: `authorize` (runs before every handler; throw `ApiError.forbidden()` to reject; the session is read through a repository function), and a Suitelet handler may return `rawResponse(...)` with return type `RawResponse` to answer with a document (CSV, PDF, a File Cabinet file) that the generated client resolves to a `Blob`; a Restlet cannot. `npm run generate` reads the controller file as source, so: handlers are inline with both types annotated, every type in the file is exported, a type is imported only from `../types/models.gen`, a service under `../services/` (copied into the generated module with the entity types it is built on) or another controller, the declaration is an object literal with literal ids, script ids are unique across controllers, and no wire shape is named `Endpoints`. A shape's name carries no controller prefix (`RolesResponse`, not `UserRolesResponse`): the generated module is scoped by controller already.
- `api/src/services/`: decisions. A service takes plain arguments (an id, a filter, one object for a create's fields), calls repository functions by their domain names, and returns a type it declares itself (`RoleSummary`, a `Pick` of an entity type; or a composition such as `ActiveUserRoles`). It never imports `N/*`, `repositories/generated/context.gen`, the repository package, or anything under `controllers/`: the controller depends on the service, never the reverse, so any controller can call any service and shape the reply its own way. Entity types from `api/src/types/models.gen` are fine.
- `api/src/repositories/`: data access. Functions read through `dbContext.<set>` from `generated/context.gen` (no tracking) and write through `dbContext.withTracking()`, kept in a local and finished before returning. A flow that reads and writes several records under one change tracker is a single repository function. `generated/` is produced by `npm run generate` and holds each model's config, field paths and the context.
- `api/src/specifications/`: query vocabulary, one module per record type of `Specification` builders. Imported by repositories only.
- `api/src/models/`: the `@RecordType` classes. A model is the declaration of a record, so its type and field ids are written on it and nowhere else; a native record type is named through `NetsuiteRecordType` from `@amerilux/netsuite-repository` (`@RecordType(NetsuiteRecordType.SALES_ORDER)`), a custom record by its id string. A model never imports `N/*`: `npm run generate` evaluates it outside NetSuite; `npm run generate` reads them into `api/src/types/models.gen.ts` (the entity interface of every model plus `<Model>Create` and `<Model>Patch`; never edit it) and `api/src/repositories/generated/`.
- A script that calls another Suitelet controller of this application server-side (the `user` restlet calling `userRoles`) does so in a repository through `createSuiteletClient<UserRolesEndpoints>(scripts.userRoles)` from `@amerilux/netsuite-api/server`, with `scripts` from the generated `api/src/scripts.gen.ts`. Only a repository builds one.
- `api/src/_host/`: the Suitelet that serves the SPA and its client script. The bundle is found by folder and file name, never by internal id.
- `client/src/routes/`: file-based routing (TanStack Router, hash history); `routeTree.gen.ts` is produced by the Vite plugin. Pages live under `client/src/pages/`, hooks under `client/src/hooks/`. `client/src/api/` is generated from the controllers: one module per controller, `<name>.gen.ts`, holding its request and response types, the entity types it names (copied in, so the client needs no copy of `models.gen.ts`), its `Endpoints` type and, unless `browser: false`, its client `api`; `index.gen.ts` re-exports each module under the controller's name. A hook imports `@/api/index.gen` and writes `user.api.roles()` or `orders.api.byId({ id })` (options such as the abort signal second), and names a shape as `user.RolesResponse`; the URL is picked from the script's `kind`. A page or component that needs `app` imports `netsuite.ts` at the project root by relative path (`../../netsuite` from `src/`). The client never imports from `api/`. A page calls a hook; only a hook calls the generated client module's `api`. Its types are the client's vocabulary: a page or component imports them freely (`import type { RoleSummary } from '@/api/user.gen'` for a prop), and a hook declares a type of its own only when it shapes or combines data for more than one page. A failed call is reported to `reportApiError` (`client/src/hooks/useApiErrors.ts`, handed to `configureApiClient` in `main.tsx`) before it rejects, and the AppShell's `ApiErrorBanner` shows it until dismissed; hooks and pages carry no error handling of their own. A page that shows a failure in place reads the query's `isError` and `error` (an `ApiClientError` whose `details` is whatever the handler gave its `ApiError`, such as a per-field validation map), and its hook passes `{ handleError: false }` to the call. A `Date` in a response shape reaches the browser as an ISO string and the generated module types it as `string`; a request shape may not carry a `Date` at all (`npm run generate` says so).
- `netsuite/`: the SDF project. `Objects/*.xml` are script records (controllers, jobs, the run record; never events); `FileCabinet/` is build output.
- Tests live in `api/__tests__/` and `client/__tests__/`; `N/*` and the wrapper's module entry points resolve to the stubs `@amerilux/netsuite-api/testing` ships (see `api/vitest.config.mts`). Test controllers (what an endpoint does with the wire: unpacking, checks, the reply), hooks, services and repositories, not UI markup. Each layer is tested against a fake of the layer below it: a repository test mocks the generated `dbContext` with a fake carrying the sets it reads, a service test mocks the repository module.

## Conventions

- **Naming.** A function name gets more specific as its responsibility narrows (`update` → `updateTransaction` → `updateTransactionShippingAddress`). A variable name gets more specific as its visibility widens (`transaction` inside a function, `vendorBillTransaction` at file scope, `vendorBillTransactionTemplate` globally). Never abbreviate. A function that produces a value of a type is `build<Type>` (`buildRoleSummary`), never `to<Type>`; the type suffix per layer (`<Model>Summary` from a service, `<Endpoint>Request` / `<Endpoint>Response` at the wire) and the verb per layer are listed in `HOW-TO-USE.md`, "Naming".
- **SuiteScript constraints.** Server handlers are synchronous. Emitted code targets ES2019, so optional chaining and nullish coalescing are downlevelled by TypeScript. `N/*` calls are rewritten to the wrapper at build time; do not add a custom externals function to `api/webpack.config.js`.
- **Script ids** are `customscript_{{prefix}}_<name>` / `customdeploy_{{prefix}}_<name>`, at most 40 characters, declared only in the controller's `defineRestlet` or `defineSuitelet` call. A job's ids end in `_mr` and are declared in its `defineJob` call, with one id per deployment it may run on; an event's ids are whatever they were given in NetSuite, and its field ids are written at the top of the event file. Record and field ids only on the model. Anything else in `netsuite.ts`.
- **Layers.** Endpoint calls service, service calls repository, repository composes specifications. A job stage sits where an endpoint does; an event sits outside the layers and may call a repository. Each layer uses the types of the layer directly below it or types it declares itself: a repository uses entity types or its own, a service what repositories return or its own, a controller what services return or its own; the generated entity types are shared vocabulary above the repository. One exception, type-only: a repository that is a Suitelet client of another script of this application takes that controller's `Endpoints` and response types, because the other script's wire is its data source. `npm run lint` enforces the imports each layer may make (endpoints and job stages never query; a service never imports from a controller; a user event takes `N/log` and repositories but no other `N/*`; a client event takes nothing of this application; a repository sees a controller file as types only, for the `Endpoints` type it builds a Suitelet client from; the client never imports from `api/`; models know nothing about the wire); a violation names the layer that should do the work instead.
- **Dependencies.** One `node_modules` at the root (npm workspaces). A workspace imports only what its own `package.json` declares; `npm run lint` fails on anything else. Add a package to the workspace that uses it, `npm install -w api <package>` (or `-w client`), never a bare `npm install <package>` at the root.
- **Logging.** A log title is the same short phrase every time (`endpoint completed`); the controller, method and record ids go in the details object. Never glue ids into a title or a details string, and never `console.log` in `api/`. With telemetry on, the wrapper adds the run id, the function, its arguments and the call chain to every line; put `@ptrk-ignore-arguments` above a function whose arguments must not be captured.
- **Outgrown rules.** The structure check and the commented blocks of `eslint.config.mjs` are this template's conventions, not the language's. A project that has moved past one deletes it (`HOW-TO-USE.md`, "Removing a rule you have outgrown") rather than working around it, and updates the docs and snippets that describe it.

## Rules

- Tests go under a `__tests__/` folder, never next to source, and are never focused or skipped.
- `netsuite.ts` imports nothing; both `api/` and `client/` bundle it directly.
- NetSuite identifiers are declared on the model that owns them (`api/src/models/`), in the controller that declares the script, or in `netsuite.ts`, never written as string literals anywhere else in `api/src/` or `client/src/`.
- Never edit generated output: `api/src/repositories/generated/`, `api/src/types/models.gen.ts`, `api/src/scripts.gen.ts`, `client/src/api/`, `client/src/routeTree.gen.ts`, `netsuite/FileCabinet/`.
- Never write secrets or account selection: no `project.json`, `client/.env`, keys or certificates, and nothing account-specific under the Vite client prefix (Vite inlines it into the uploaded bundle). Update `.env.example` instead.
- Run `npm test` and `npm run typecheck` before a commit, and `npm test` before any deploy. Deploying is a human action: do not run `npm run deploy` or `suitecloud` uploads unless asked.
- No recursive force deletes, no `--no-verify`, no force push without `--force-with-lease`.

## Guardrails

Probity (`probity.config.ts`, hooked into Claude Code through `.claude/settings.json`) enforces the rules of this repository mechanically and blocks: destructive commands, commits without tests and typecheck, deploys without tests, imports in `netsuite.ts`, NetSuite ids as string literals outside the models, the controllers and `netsuite.ts`, writes to generated output or secret files, colocated or focused tests. It also requires a failing test first for controllers, job stages, services, repositories and client hooks. Its judge sees tool calls and their output, not prose, so give it evidence: before a refactor, run the affected test file so the green is in the recent session, and run it again after; before a behaviour change, run the changed or added test and let it fail visibly. A refactor is one where no existing assertion has to change; anything that needs a new or changed assertion is behaviour and starts with the red. When a block fires, fix the cause rather than working around it.
